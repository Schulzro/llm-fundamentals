LoRA / QLoRA : fine-tuning sans le coût complet

~25 min · Objectif entretien : expliquer le mécanisme de LoRA, la quantification dans QLoRA, et justifier leurs avantages (mémoire, coût, flexibilité)

LoRA et QLoRA sont les techniques qui ont démocratisé le fine-tuning des grands modèles. Avant LoRA, fine-tuner un modèle de 70B paramètres nécessitait des dizaines de GPU A100. Avec LoRA, on peut le faire sur un seul GPU. Avec QLoRA, même sur une carte grand public. En entretien, c'est la question PEFT (Parameter-Efficient Fine-Tuning) la plus fréquente — et celle qui montre que vous comprenez les compromis entre performance et ressources.

Cette leçon couvre : le problème du fine-tuning complet, le mécanisme de LoRA (Low-Rank Adaptation), l'ajout de la quantification dans QLoRA, puis les cas d'usage, avantages et limites.

1 · Le problème : le fine-tuning complet est prohibitif

Mémoire · Coût · Catastrophic Forgetting

Fine-tuner un LLM de taille moyenne (7B-70B) nécessite des ressources énormes. 

Coût du fine-tuning complet pour un modèle de 70B paramètres :

Mémoire (FP16) :
  • Paramètres du modèle      : 70B × 2 bytes = 140 Go
  • Gradients                : 140 Go
  • Optimizer states (Adam)  : 140 Go × 2 = 280 Go
  • Activation checkpointing : ~140 Go
  └─────────────────────────────────────────────┘
                              Total : ~700 Go par GPU

Nombre de GPU nécessaires :
  • A100 (40 Go)  : 700 / 40 = 17.5 → 18 GPU minimum
  • A100 (80 Go)  : 700 / 80 = 8.75 → 9 GPU minimum
  • H100 (80 Go)  : même calcul

Coût estimé (cloud) :
  • 9 × A100 @ $3/h = $27/h
  • Pour 1 époque sur 100k exemples : ~$2,700
  • Pour un entraînement complet : $10,000-$50,000+

Problèmes supplémentaires :
  • Catastrophic forgetting : le modèle oublie ses connaissances générales
  • Temps d'entraînement : des heures à des jours
  • Stockage : besoin de sauvegarder le modèle complet

La solution : ne pas entraîner tous les paramètres, mais seulement une petite partie qui capture les adaptations nécessaires pour la tâche.

2 · L'intuition LoRA : adapter avec des matrices de faible rang

Low-Rank Adaptation · ΔW = BA

LoRA (Hu et al., 2021) part d'une hypothèse simple : les poids d'un modèle pré-entraîné n'ont pas besoin d'être mis à jour de manière arbitraire. Les changements nécessaires pour une tâche spécifique peuvent être représentés par des matrices de faible rang.

Au lieu de mettre à jour W directement, LoRA gèle les poids originaux W et ajoute une adaptation de faible rang :

Formule LoRA :

  h = Wx + ΔWx        où ΔW = BA
  h = Wx + BAx

  W  ∈ ℝ^{d×k}  : poids originaux (figés)
  B  ∈ ℝ^{d×r}  : matrice de projection (entraînée)
  A  ∈ ℝ^{r×k}  : matrice d'expansion (entraînée)
  r  : rang (hyperparamètre, typiquement 8-64)

Nombre de paramètres entraînables :
  • Sans LoRA : d × k
  • Avec LoRA : (d × r) + (r × k) = r × (d + k)
  
Réduction :
  • Si r=8, d=4096, k=4096 : 8×(4096+4096) = 65,536 vs 16,777,216
  • Ratio : 65K / 16M = 0.4% des paramètres !

Où appliquer LoRA ? Typiquement sur les matrices de projection dans l'attention :

  • Q, K, V, O dans les couches d'attention (self-attention)
  • Parfois aussi sur les couches feed-forward (MLP)
  • Pas sur les embeddings ou le LayerNorm (peu de gains)

3 · QLoRA : ajouter la quantification pour aller plus loin

4-bit NormalFloat · Double Quantification

QLoRA (Dettmers et al., 2023) combine LoRA avec la quantification pour réduire encore plus la mémoire. L'idée : quantifier le modèle de base (figé) en 4 bits, et n'entraîner que les adapteurs LoRA en 16 bits. 

Quantification 4-bit NormalFloat (NF4) :

  • Les poids sont stockés en 4 bits (16 valeurs possibles)
  • Mais les calculs se font en float16/float32
  • Technique de déquantification à la volée

  Mémoire pour un modèle de 70B :
    • Sans quantification (FP16) : 70B × 2 = 140 Go
    • Avec NF4               : 70B × 0.5 = 35 Go
    • Gain                   : 4× moins de mémoire

  QLoRA = LoRA + Quantification :
    • Modèle de base          : 4 bits (figé, non entraîné)
    • Adapteurs LoRA          : 16 bits (entraînés)
    • Activations             : 16 bits (pendant le forward)
    • Gradients               : 16 bits (pendant le backward)
    
    Mémoire totale pour 70B : ~40-50 Go (vs 700 Go sans LoRA/QLoRA)
    → Tient sur un seul GPU A100 (40 Go) ou même RTX 4090 (24 Go) !

Double Quantification (pour les très grands modèles) :

  • Quantifier une première fois les poids en 8 bits
  • Quantifier une deuxième fois les poids déjà quantifiés en 4 bits
  • Permet de réduire encore la mémoire sans perte significative de performance

4 · Avantages : pourquoi tout le monde utilise LoRA/QLoRA

Le compromis est clair : avec LoRA/QLoRA, on sacrifie 5-15% de performance pour diviser le coût par 10 à 100. C'est un échange que presque tout le monde accepte.

5 · Cas d'usage : quand utiliser LoRA vs QLoRA

Scénarios · Bonnes pratiques

LoRA et QLoRA ne sont pas interchangeables. Chaque méthode a ses cas d'usage optimaux.

Utiliser LoRA (sans quantification) quand :

  • Vous avez des GPU avec beaucoup de mémoire (A100 80 Go, H100)
  • La performance est critique et vous ne voulez pas sacrifier les 5-10% de QLoRA
  • Vous entraînez sur des tâches complexes où chaque point de performance compte
  • Vous voulez une compatibilité maximale avec les bibliothèques existantes
  • Modèles de taille moyenne (7B-13B) où la quantification apporte moins de gains

Utiliser QLoRA quand :

  • Vous avez des ressources limitées (1-2 GPU, RTX 4090)
  • Vous travaillez avec des très grands modèles (30B-70B+)
  • Le coût est un facteur critique
  • Vous faites du prototypage rapide et voulez itérer vite
  • Vous avez besoin de fine-tuner plusieurs tâches en parallèle

Bonnes pratiques générales :

  • Rang (r) : Commencez avec r=8 ou 16, puis augmentez si nécessaire. r=32 ou 64 pour des tâches complexes.
  • Alpha (α) : Hyperparamètre de LoRA. Typiquement α=2×r ou α=16.
  • Dropout : Ajoutez du dropout sur les adapteurs LoRA (0.05-0.1) pour éviter le surapprentissage.
  • Modules cibles : Appliquez LoRA sur Q, V (au minimum). Pour plus de performance : Q, K, V, O.
  • Taux d'apprentissage : Plus élevé que le full fine-tuning (typiquement 1e-4 à 5e-4 vs 1e-5).
  • Batch size : Peut être plus petit grâce à la réduction de mémoire.

6 · Limites et pièges à éviter

Quand LoRA/QLoRA ne suffisent pas

LoRA et QLoRA ne sont pas des solutions magiques. Il y a des cas où le fine-tuning complet reste nécessaire.

LimiteExplicationSolution
Performance limitée LoRA/QLoRA atteignent 85-98% de la performance du full fine-tuning Augmenter r, utiliser plus de modules, ou passer au full fine-tuning
Tâches très différentes Si la tâche est trop éloignée du pré-entraînement, les adapteurs ne suffisent pas Full fine-tuning ou adapter plus de couches
Quantification instable QLoRA peut être instable avec certains optimiseurs Utiliser des optimiseurs adaptés (paged_adamw, bitsandbytes)
Latence d'inférence La déquantification à la volée ajoute de la latence Utiliser des bibliothèques optimisées (bitsandbytes, torch.compile)
Compatibilité Tous les modèles ne supportent pas LoRA/QLoRA Vérifier la compatibilité avant de commencer
Choix de r Un r trop petit limite la capacité, un r trop grand annule les gains Faire des tests avec différents r (8, 16, 32, 64)

Quand utiliser le full fine-tuning malgré tout ?

  • Pour des tâches critiques où chaque point de performance compte
  • Quand vous avez les ressources et que le coût n'est pas un problème
  • Pour des modèles relativement petits (<7B) où LoRA apporte peu de gains
  • Quand vous voulez éviter toute complexité d'implémentation

7 · Implémentation pratique : code et bibliothèques

PEFT · bitsandbytes · Transformers 
Exemple avec la bibliothèque PEFT (Hugging Face) :

from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM

# Charger le modèle de base
model = AutoModelForCausalLM.from_pretrained("mistralai/Mistral-7B")

# Configuration LoRA
lora_config = LoraConfig(
    r=16,                    # rang
    lora_alpha=32,          # alpha
    target_modules=["q_proj", "v_proj"],  # modules cibles
    lora_dropout=0.05,      # dropout
    bias="none",            # pas de biais
    task_type="CAUSAL_LM"  # type de tâche
)

# Appliquer LoRA
model = get_peft_model(model, lora_config)

# Entraînement (comme un fine-tuning normal)
trainer.train()

# Sauvegarder (seulement les adapteurs)
model.save_pretrained("mistral-7b-lora")
Exemple QLoRA avec bitsandbytes :

from peft import LoraConfig
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
import torch

# Configuration de quantification
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,      # charger en 4 bits
    bnb_4bit_use_double_quant=True,  # double quantification
    bnb_4bit_quant_type="nf4",      # type de quantification
    bnb_4bit_compute_dtype=torch.float16  # calcul en FP16
)

# Charger le modèle quantifié
model = AutoModelForCausalLM.from_pretrained(
    "mistralai/Mistral-7B",
    quantization_config=bnb_config,
    device_map="auto"      # répartition automatique sur les GPU
)

# Configuration LoRA (même que avant)
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM"
)

# Appliquer LoRA
model = get_peft_model(model, lora_config)

# Entraînement (les adapteurs sont en FP16, le reste en 4 bits)
trainer.train()

8 · Les pièges d'entretien

PiègeLa bonne réponse
« LoRA entraîne tous les paramètres du modèle » Non : LoRA gèle les poids originaux et n'entraîne que les matrices BA de faible rang.
« QLoRA quantifie aussi les adapteurs LoRA » Non : dans QLoRA, seul le modèle de base est quantifié (en 4 bits). Les adapteurs restent en 16 bits.
« LoRA donne les mêmes résultats que le full fine-tuning » Non : LoRA atteint 85-98% de la performance, pas 100%. C'est un compromis mémoire/performance.
« Plus le rang r est élevé, mieux c'est » Non : un r trop élevé annule les gains de mémoire. Il faut trouver le bon compromis (typiquement 8-64).
« LoRA est seulement pour les petits modèles » Non : LoRA est surtout utile pour les GRANDS modèles, où le full fine-tuning est prohibitif.
« QLoRA fonctionne avec n'importe quel GPU » Non : QLoRA nécessite un GPU avec suffisamment de mémoire pour les activations (minimum 24 Go pour 70B).
« LoRA évite complètement le catastrophic forgetting » Non : LoRA réduit le risque, mais ne l'élimine pas complètement. Le modèle de base reste figé.
« Les adapteurs LoRA sont spécifiques à une tâche » Oui, c'est correct — mais c'est aussi une force : on peut avoir plusieurs adapteurs pour un même modèle de base.

C.A.T. — « Expliquez LoRA et comment il réduit le coût du fine-tuning. »

Classify : « LoRA est une technique de fine-tuning efficace en paramètres qui permet d'adapter un grand modèle avec très peu de paramètres supplémentaires. »

Apply : « Au lieu de mettre à jour tous les poids du modèle, LoRA gèle les poids originaux W et ajoute une adaptation de faible rang ΔW = BA, où B est une matrice d×r et A est une matrice r×k, avec r beaucoup plus petit que d et k (typiquement 8-64). Pendant l'entraînement, seuls B et A sont mis à jour. Pour un modèle de 70B, cela réduit le nombre de paramètres entraînables de 70 milliards à quelques millions seulement. »

Trap : « Le piège serait de penser que LoRA n'a pas d'impact sur la performance. En réalité, on sacrifie 5-15% de performance pour diviser le coût par 10. C'est un compromis que la plupart des praticiens acceptent volontiers. »

C.A.T. — « Quelle est la différence entre LoRA et QLoRA ? »

Classify : « LoRA et QLoRA sont tous deux des méthodes de fine-tuning efficace, mais QLoRA ajoute la quantification pour réduire encore plus la mémoire. »

Apply : « LoRA gèle le modèle de base et entraîne seulement des adapteurs de faible rang. QLoRA va plus loin en quantifiant le modèle de base en 4 bits (avec NF4), ce qui réduit la mémoire du modèle de base de 8× (par rapport à FP16). Les adapteurs LoRA restent en 16 bits pour maintenir la précision pendant l'entraînement. Résultat : on peut fine-tuner un modèle de 70B sur un seul GPU A100 au lieu de 18. »

Trap : « Le piège serait de penser que QLoRA quantifie aussi les adapteurs. Non, seuls les poids du modèle de base sont quantifiés. Les adapteurs restent en pleine précision pour garantir la stabilité de l'entraînement. »

C.A.T. — « Pourquoi utiliser LoRA plutôt que le full fine-tuning ? »

Classify : « Parce que LoRA permet de réduire considérablement le coût et la mémoire nécessaires pour le fine-tuning. »

Apply : « Pour fine-tuner un modèle de 70B, le full fine-tuning nécessite environ 700 Go de mémoire GPU (avec les gradients et l'optimiseur), ce qui veut dire 18 GPU A100. Avec LoRA, on n'entraîne que quelques millions de paramètres, donc la mémoire est proportionnelle à ces paramètres seulement. On passe de 18 GPU à 2-4 GPU. De plus, on peut sauvegarder et charger uniquement les adapteurs (quelques Mo) au lieu du modèle complet (140 Go). »

Trap : « Mais attention : ce n'est pas gratuit. On sacrifie un peu de performance (5-15%), et il faut bien choisir le rang r et les modules cibles. Mais dans 90% des cas, c'est un compromis très acceptable. »
