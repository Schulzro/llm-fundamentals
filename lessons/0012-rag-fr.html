Leçon 12 · Fondamentaux des LLM · Tier 4 — Comment les LLM sont déployés

RAG : pipeline end-to-end, chunking, retrieval

~28 min · Objectif entretien : dérouler le pipeline RAG complet, expliquer les stratégies de chunking, comparer dense vs sparse retrieval, et nommer les métriques d'évaluation

RAG (Retrieval-Augmented Generation) est la technique la plus populaire pour donner aux LLM l'accès à des connaissances externes. Sans RAG, un LLM ne peut répondre qu'avec ce qu'il a appris pendant le pré-entraînement. Avec RAG, il peut accéder à des documents spécifiques, des bases de connaissances privées, ou des informations en temps réel. En entretien, c'est la question système la plus demandée — et celle qui sépare ceux qui savent utiliser un LLM de ceux qui savent construire un système complet.

Cette leçon couvre : le pipeline RAG complet, les stratégies de chunking, dense vs sparse retrieval, le re-ranking, puis les métriques d'évaluation et les pièges courants.

1 · Le pipeline RAG : de l'ingestion à la génération

Ingest → Chunk → Embed → Retrieve → Generate

2 · Chunking : l'art de bien découper les documents

Taille · Chevauchement · Stratégies

Le chunking est l'étape la plus sous-estimée du RAG — et pourtant la plus critique. Un mauvais chunking = retrieval médiocre = réponses médiocres.

Taille des chunks : le compromis

TailleAvantagesInconvénientsCas d'usage
Petits (128-256 tokens) Précision fine, moins de bruit Perte de contexte, coupures de phrases Documents très structurés (tableaux, listes)
Moyens (512-1024 tokens) Bon équilibre contexte/précision Peut inclure du bruit Cas général (articles, documentation)
Grands (2048+ tokens) Contexte complet, pas de coupures Bruit important, coût élevé Documents très longs (livres, rapports)

Stratégies de chunking

Stratégies de découpage :

1. FIXE (Fixed Size Chunking)
   • Découper tous les N tokens
   • Simple à implémenter
   • Risque : coupure en plein milieu d'une phrase

2. PAR PHRASE (Sentence Window)
   • Découper aux limites de phrases
   • Meilleure cohérence sémantique
   • Nécessite un tokeniseur de phrases

3. PAR PARAGRAPHE
   • Utiliser la structure du document
   • Bon pour les articles, la documentation
   • Peut donner des chunks de tailles très variables

4. RÉCURSIF (Recursive Character Text Splitter)
   • Essayer de découper par : ["\n\n", "\n", ".", ",", " "]
   • Garantit des chunks cohérents
   • Implémentation dans LangChain

5. AVEC CHEVAUCHEMENT (Overlapping Chunks)
   • Chaque chunk chevauche le précédent de X tokens
   • X typique : 50-200 tokens (20-25% de la taille du chunk)
   • Évite les problèmes de coupure aux limites
   • Augmente le nombre de chunks (et donc le coût)

Bonnes pratiques

  • Taille par défaut : 512-1024 tokens avec 20% de chevauchement
  • Respecter les limites de tokens : ne pas dépasser la fenêtre de contexte du LLM
  • Nettoyer avant de chunker : supprimer les en-têtes, pieds de page, navigation
  • Conserver les métadonnées : source, page, position pour le retrieval
  • Tester plusieurs stratégies : le chunking optimal dépend du type de documents

3 · Embedding : transformer le texte en vecteurs

Modèles · Dimension · Normalisation

L'embedding est la représentation vectorielle du texte qui permet la recherche sémantique. Deux textes sémantiquement proches auront des embeddings proches dans l'espace vectoriel.

Modèles d'embedding populaires

ModèleFournisseurDimensionCas d'usageAvantages
text-embedding-ada-002 OpenAI 1536 Général Bonne performance, standard de l'industrie
bge-small / bge-base BAAI 384 / 768 Général / Multilingue Open source, bon rapport qualité/prix
all-MiniLM Sentence Transformers 384 Général Léger, rapide, open source
e5-large Intfloat 1024 Recherche avancée Très bonne performance sur les benchmarks
instructor HKUNLP 768 Embeddings avec instructions Permet de spécifier la tâche dans le prompt

Normalisation

Normalisation des embeddings :

  • Normalisation L2 (recommandée) :
    x_normalized = x / ||x||_2
    
  • Avantages :
    - La similarité cosinus = produit scalaire (plus rapide)
    - Évite les problèmes d'échelle
    - Meilleure performance en pratique
    
  • Quand normaliser ?
    - Toujours pour la recherche (query et documents)
    - Optionnel pour le stockage (mais recommandé)
    
  • Similarité cosinus :
    similarity(a, b) = (a · b) / (||a|| ||b||)
    
    Avec normalisation L2 : similarity(a, b) = a · b

Bonnes pratiques

  • Utiliser le même modèle pour query et documents
  • Normaliser les embeddings (L2 norm)
  • Tester plusieurs modèles sur vos données
  • Considérer la dimension : plus haute = plus précis mais plus lent et plus de mémoire
  • Batch processing : générer les embeddings par lots pour optimiser

4 · Retrieval : trouver les bons chunks

Dense vs Sparse · k-NN · Re-ranking

Le retrieval est le cœur du RAG. Une mauvaise recherche = une mauvaise réponse, même avec le meilleur LLM du monde.

Dense Retrieval vs Sparse Retrieval

CritèreDense RetrievalSparse Retrieval (BM25)
Représentation Vecteurs denses (embeddings) Mots-clés (TF-IDF, BM25)
Sémantique ✅ Comprend le sens (synonymes, paraphrases) ❌ Basé sur les mots exacts
Vitesse ⚡ Très rapide avec index vectoriel ⚡⚡ Très rapide (algorithmes matures)
Mémoire Élevée (stockage des vecteurs) Faible (stockage des termes inversés)
Prétraitement Nécessite l'embedding de tous les documents Aucun (utilise le texte brut)
Performance ✅✅ Excellente pour les requêtes sémantiques ✅ Bonne pour les requêtes avec mots-clés exacts
Cas d'usage Questions en langage naturel, recherche sémantique Recherche par mots-clés, documents structurés

Hybrid Retrieval : le meilleur des deux mondes

Hybrid Retrieval = Dense + Sparse

  • Combiner les scores des deux méthodes
  • Méthodes de combinaison :
    - Addition simple : score_final = score_dense + score_sparse
    - Pondération : score_final = α·score_dense + (1-α)·score_sparse
    - RRF (Reciprocal Rank Fusion) : méthode robuste sans réglage de α

  RRF (formule) :
    score_RRF = 1 / (k + rank_dense) + 1 / (k + rank_sparse)
    où k est un paramètre de normalisation (typiquement k=60)

  Avantages de l'hybride :
    ✅ Meilleure couverture (capture à la fois sémantique et mots-clés)
    ✅ Plus robuste aux différentes formulations de requêtes
    ✅ Meilleure performance globale dans la plupart des benchmarks

Re-ranking : affiner les résultats

Le re-ranking est l'étape secrète pour améliorer la qualité du retrieval. Après une première recherche rapide (avec dense ou sparse), on utilise un modèle plus puissant pour réordonner les résultats. 

Re-ranking avec Cross-Encoder :

  Étape 1 : Retrieval initial (rapide)
    • Utiliser un bi-encoder (dense) ou BM25
    • Récupérer k=50-100 chunks candidats
    
  Étape 2 : Re-ranking (plus lent mais précis)
    • Utiliser un cross-encoder (ex: BERT, RoBERTa)
    • Le cross-encoder prend [query, document] comme entrée
    • Il calcule un score de pertinence plus précis
    • Sélectionner les top k=3-10 chunks finaux

  Modèles de re-ranking populaires :
    • bge-reranker (BAAI)
    • FlagModel/BAAI-bge-reranker-base
    • cross-encoder/ms-marco-MiniLM-L-6-v2
    • cross-encoder/ms-marco-MiniLM-L-12-v2

  Avantages :
    ✅ Meilleure précision (le cross-encoder voit query+document ensemble)
    ✅ Compromis vitesse/précision optimal
    
  Inconvénients :
    ❌ Plus lent (nécessite de passer chaque paire [query, doc] dans le modèle)
    ❌ Plus de ressources computationnelles

Index vectoriels

Types d'index vectoriels :

  1. HNSW (Hierarchical Navigable Small World)
     • Algorithme : graphe hiérarchique
     • Avantages : très rapide, bonne précision
     • Inconvénients : mémoire élevée
     • Implémentations : FAISS, Weaviate, Qdrant
     
  2. IVF (Inverted File Index)
     • Algorithme : partitionnement + recherche dans les partitions
     • Avantages : faible mémoire, bon pour les grands datasets
     • Inconvénients : précision légèrement inférieure
     • Implémentations : FAISS
     
  3. PQ (Product Quantization)
     • Algorithme : compression des vecteurs
     • Avantages : réduit la mémoire de 4-16×
     • Inconvénients : perte de précision
     • Souvent combiné avec IVF (IVF-PQ)
     
  4. LSH (Locality-Sensitive Hashing)
     • Algorithme : hachage aléatoire
     • Avantages : très rapide pour l'indexation
     • Inconvénients : précision limitée
     
  Bases vectorielles populaires :
    • FAISS (Facebook) : bibliothèque C++ optimisée
    • Weaviate : base vectorielle open source avec API
    • Pinecone : service managé
    • Qdrant : base vectorielle open source
    • Milvus : base vectorielle distribuée

5 · La triade RAG : relevance, faithfulness, answer

Les 3 piliers de l'évaluation RAG

Un bon système RAG doit exceller sur trois dimensions. Optimiser une seule dimension au détriment des autres donne un système déséquilibré.

🎯 Relevance

Les documents récupérés sont-ils pertinents pour la question ?

  • Métrique : précision@k, recall@k
  • Outils : évaluation humaine, LLM-as-judge
  • Amélioration : meilleur embedding, re-ranking

📜 Faithfulness

La réponse est-elle fidèle aux documents récupérés ?

  • Métrique : faithfulness score, citation recall
  • Outils : vérification des citations, détection d'hallucinations
  • Amélioration : prompt engineering, vérification post-génération

✅ Answer

La réponse est-elle correcte et utile ?

  • Métrique : exact match, F1 score, utilité perçue
  • Outils : évaluation humaine, benchmarks standard
  • Amélioration : meilleur LLM, prompt optimisé

Exemple concret :

  • Bonne relevance, mauvaise faithfulness : Le système récupère les bons documents, mais le LLM invente des informations qui ne sont pas dans les documents.
  • Bonne faithfulness, mauvaise relevance : Le système récupère des documents non pertinents, mais la réponse est fidèle à ces documents (donc fausse).
  • Bonne relevance et faithfulness, mauvaise answer : Les documents sont pertinents et la réponse leur est fidèle, mais elle ne répond pas vraiment à la question.

6 · Évaluation : comment mesurer la qualité d'un système RAG

Métriques · Ragas · Benchmarks

Évaluer un système RAG est complexe. Contrairement aux tâches classiques de ML, il n'y a pas de métrique unique qui capture tout.

Métriques RAG (Ragas)

Ragas est une bibliothèque Python spécialement conçue pour évaluer les systèmes RAG. Elle implémente plusieurs métriques alignées sur la triade RAG :

MétriqueDescriptionDimensionPlage
Answer Relevancy La réponse est-elle pertinente pour la question ? Answer 0-1
Faithfulness La réponse est-elle fidèle aux documents récupérés ? Faithfulness 0-1
Context Relevancy Les documents récupérés sont-ils pertinents pour la question ? Relevance 0-1
Context Recall Tous les documents pertinents ont-ils été récupérés ? Relevance 0-1
Context Precision Seuls les documents pertinents ont-ils été récupérés ? Relevance 0-1
Latency Temps de réponse (retrieval + génération) Performance ms
Cost Coût par requête (tokens input + output) Performance $

LLM-as-Judge

LLM-as-Judge : utiliser un LLM pour évaluer les réponses

  Avantages :
    ✅ Flexible (peut évaluer n'importe quelle dimension)
    ✅ Pas besoin de données labellisées
    ✅ Peut donner des feedbacks détaillés
    
  Inconvénients :
    ❌ Coûteux (chaque évaluation = une inférence LLM)
    ❌ Subjectif (dépend du LLM juge)
    ❌ Nécessite un prompt d'évaluation bien conçu
    
  Exemple de prompt d'évaluation :
    
  """
  Tu es un évaluateur strict. Évalue la réponse suivante selon ces critères :
  1. Relevance : La réponse répond-elle à la question ? (1-5)
  2. Faithfulness : La réponse est-elle fidèle aux documents fournis ? (1-5)
  3. Utilité : La réponse est-elle utile pour l'utilisateur ? (1-5)
  
  Question : {question}
  Documents : {documents}
  Réponse : {answer}
  
  Donne un score pour chaque critère et une justification.
  """

Benchmarks RAG

  • BEIR : Benchmark pour l'évaluation du retrieval
  • MTEB (Massive Text Embedding Benchmark) : évaluation des modèles d'embedding
  • RAGTruth : benchmark spécifique au RAG
  • CRAG (Correctness and Relevance Assessment for Grounding) : évaluation de la correction et de la pertinence

7 · Pièges courants et bonnes pratiques

Erreurs · Solutions · Optimisations

Le RAG semble simple, mais il y a de nombreux pièges. Voici les erreurs les plus courantes et comment les éviter.

Pièges courants

PiègeConséquenceSolution
Chunks trop grands Bruit dans le retrieval, documents non pertinents Utiliser des chunks de 512-1024 tokens
Pas de chevauchement Information coupée entre les chunks Ajouter 20% de chevauchement
Embeddings non normalisés Mauvaise performance de recherche Normaliser les embeddings (L2 norm)
k trop petit Pas assez de contexte pour le LLM Utiliser k=3-10 selon la complexité
k trop grand Trop de bruit, coût élevé Limiter k et utiliser le re-ranking
Pas de re-ranking Précision limitée avec dense retrieval seul Ajouter un cross-encoder pour le re-ranking
Prompt mal construit Le LLM ignore le contexte RAG Utiliser des instructions claires : "Utilise les documents suivants pour répondre..."
Pas de citations Impossible de vérifier la faithfulness Demander au LLM de citer ses sources
Documents non nettoyés Bruit dans les embeddings et le retrieval Nettoyer les documents avant l'ingestion
Index non mis à jour Documents obsolètes dans les résultats Mettre en place un pipeline de mise à jour

Bonnes pratiques générales

  • Commencer simple : dense retrieval + petit k, puis complexifier
  • Évaluer à chaque étape : retrieval seul, puis RAG complet
  • Monitorer les métriques : relevance, faithfulness, answer quality
  • Optimiser pour le coût : limiter le nombre de tokens dans le prompt
  • Tester avec des requêtes réelles : pas seulement des benchmarks
  • Itérer rapidement : le RAG est un processus itératif

8 · Les pièges d'entretien

PiègeLa bonne réponse
« RAG permet au LLM d'apprendre de nouveaux faits » Non : RAG donne accès à des informations externes, mais le LLM ne les « apprend » pas. Il les utilise juste pour la réponse actuelle.
« RAG remplace le fine-tuning » Non : RAG et fine-tuning sont complémentaires. RAG pour l'information externe, fine-tuning pour les compétences et le style.
« Plus on récupère de documents, mieux c'est » Non : trop de documents = bruit. Il faut trouver le bon k (typiquement 3-10).
« RAG est toujours plus rapide que le fine-tuning » Non : le retrieval peut être lent avec des grands index. De plus, le prompt RAG est plus long.
« RAG élimine les hallucinations » Non : RAG réduit les hallucinations, mais ne les élimine pas. Le LLM peut encore inventer des informations.
« Dense retrieval est toujours meilleur que sparse » Non : sparse (BM25) est meilleur pour les requêtes avec mots-clés exacts. Dense est meilleur pour les requêtes sémantiques.
« Le chunking n'a pas d'importance » Non : le chunking est critique. Un mauvais chunking = retrieval médiocre = réponses médiocres.
« RAG fonctionne avec n'importe quel LLM » Oui, c'est correct — mais les petits modèles peuvent avoir du mal à utiliser efficacement le contexte RAG.

C.A.T. — « Expliquez le pipeline RAG de bout en bout. »

Classify : « RAG (Retrieval-Augmented Generation) est une technique qui permet à un LLM d'accéder à des informations externes pour améliorer ses réponses. »

Apply : « Le pipeline RAG se compose de 6 étapes : 1) Ingestion des documents, 2) Chunking (découpage en morceaux de 512-1024 tokens avec chevauchement), 3) Embedding (vectorisation avec un modèle comme text-embedding-ada-002), 4) Indexation (stockage dans une base vectorielle comme FAISS ou Weaviate), 5) Retrieval (récupération des k chunks les plus pertinents avec dense ou sparse retrieval), et 6) Génération (construction du prompt avec le contexte RAG et réponse du LLM). »

Trap : « Le piège serait de penser que RAG est juste 'ajouter des documents'. En réalité, chaque étape a un impact critique. Par exemple, un mauvais chunking peut rendre le retrieval inefficace, même avec le meilleur modèle d'embedding. »

C.A.T. — « Quelle est la différence entre dense et sparse retrieval ? »

Classify : « Dense retrieval utilise des embeddings vectoriels pour capturer la sémantique, tandis que sparse retrieval utilise des mots-clés et des statistiques comme TF-IDF ou BM25. »

Apply : « Dense retrieval représente chaque document par un vecteur dense (384-1024 dimensions) généré par un modèle de langage. La similarité est calculée avec la similarité cosinus. Sparse retrieval, comme BM25, utilise une représentation creuse basée sur les termes du document et leurs fréquences. Dense est meilleur pour les requêtes sémantiques ('Quels sont les symptômes de la grippe ?'), tandis que sparse est meilleur pour les requêtes avec mots-clés exacts ('document PDF section 3.2'). »

Trap : « Le piège serait de choisir une seule méthode. En pratique, l'approche hybride (dense + sparse avec RRF) donne les meilleurs résultats, car elle combine les forces des deux approches. »

C.A.T. — « Pourquoi le chunking est-il important en RAG ? »

Classify : « Le chunking est l'étape qui détermine comment les documents sont découpés avant l'embedding et le retrieval. »

Apply : « Si les chunks sont trop grands, on récupère des documents avec beaucoup de bruit. Si les chunks sont trop petits, on perd le contexte et on peut couper des informations importantes au milieu. Une bonne pratique est d'utiliser des chunks de 512-1024 tokens avec 20% de chevauchement. Par exemple, avec un document de 2000 tokens et des chunks de 512 tokens avec 100 tokens de chevauchement, on obtient 5 chunks : [0-512], [412-924], [824-1336], [1236-1748], [1648-2000]. »

Trap : « Le piège serait de penser que le chunking est une étape secondaire. En réalité, c'est souvent l'étape la plus critique après le choix du modèle d'embedding. Un mauvais chunking peut rendre même le meilleur retrieval inefficace. »

C.A.T. — « Comment évaluez-vous un système RAG ? »

Classify : « On évalue un système RAG selon trois dimensions principales : relevance, faithfulness, et answer quality. »

Apply : « La relevance mesure si les documents récupérés sont pertinents pour la question. On peut l'évaluer avec la précision@k ou le recall@k. La faithfulness mesure si la réponse est fidèle aux documents récupérés, sans inventer d'informations. On peut utiliser des métriques comme le faithfulness score ou vérifier manuellement les citations. Enfin, l'answer quality mesure si la réponse est correcte et utile pour l'utilisateur. Des bibliothèques comme Ragas implémentent ces métriques automatiquement. »

Trap : « Le piège serait de se concentrer sur une seule métrique. Par exemple, optimiser seulement la relevance peut donner des documents pertinents, mais le LLM peut quand même produire une réponse incorrecte (mauvaise faithfulness ou answer quality). Il faut équilibrer les trois dimensions. »
