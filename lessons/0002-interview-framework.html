The Interview Framework: Answer in 60s, Signal Depth

~15 min · Applies to every LLM technical question, not just caching

The problem with most technical answers

Two failure modes in applied AI interviews:

  • Too shallow — "I'd use prompt caching to save money." Full stop. No mechanism, no tradeoff, no signal that you've shipped this.
  • Too deep, too fast — You spend 3 minutes on TTL math before the interviewer has understood the basic concept. You lose them and run out of time.

What you want: a tight core answer the interviewer can follow in 45 seconds, followed by a single signal sentence that invites them to go deeper if they want to. You control the depth dial. They decide whether to turn it.

The framework: C.A.T.

C — Classify the type of problem (what LLM primitive does this map to?)
A — Apply the mechanism to their specific scenario (the what and the how)
T — Trap one gotcha or tradeoff (signals you've hit this in production)

Three moves, in order, in 60 seconds. The Trap is what separates candidates who've read the docs from candidates who've shipped the thing. It's the sentence that makes the interviewer lean forward.

After T, you pause. If they want more, you have a full depth map ready. But you don't unload it unprompted.

The depth map — what lives behind each answer

Every good technical answer has three layers. Know all three. Deliver layer 1 by default. Signal layer 2 briefly. Keep layer 3 in your pocket.

LayerWhat it isWhen to surface it
1 — Mechanism How it works (the invariant, the API, the basic flow) Always — this is your core answer
2 — Tradeoff When it helps vs hurts, cost/latency implications Your "Trap" sentence; expand if they probe
3 — Edge case Silent invalidators, minimum token thresholds, concurrent-request timing Only when they ask "what could go wrong?" or "how would you debug it?"

Worked example: the handbook chatbot question

"You're building a chatbot that helps users analyze their 50-page company handbook, and users ask various questions about it throughout their session. How would prompt caching help here, and what part of your prompt would you actually want to cache?"

Step 1 — Classify

This is a large shared context + variable queries pattern. One expensive static document, many cheap dynamic questions. That's the textbook use case for prompt caching — cache the document, not the questions.

Step 2 — Apply

Place the handbook as a content block early in the prompt — in the system prompt or as the first user message — and mark a cache_control breakpoint at its end. Leave it byte-identical across every request. Each user question sits after the breakpoint and is processed fresh. The expensive KV computation of processing the handbook is stored and replayed from cache — you pay ~10% of the normal cost to reuse it, rather than reprocessing it from scratch. The handbook bytes still travel in every request; what's cached is the computation, not model memory (the model is stateless per request).

Step 3 — Trap

"The one thing that kills this silently is injecting anything dynamic into the cached block — a timestamp, the user's name, the current date. One dynamic byte before the breakpoint and every request pays full price with no error to tell you."

The full 60-second answer, spoken:

"This is a large-static-context plus variable-queries pattern — textbook caching territory. I'd put the handbook in the system prompt with a cache breakpoint at the end, and keep it frozen for the session. Every question the user asks sits after that breakpoint and gets processed fresh, but the 40,000-token handbook is served from cache at about one-tenth the cost. The gotcha is anything dynamic in the cached block — a date, a user ID, even a reordered JSON key — silently invalidates it. So I'd keep the handbook completely static and push all personalization into the message turns."

Then stop. The interviewer now knows you understand the mechanism, the application, and a real failure mode. If they want the TTL math, the minimum token threshold, or how to debug a miss — they'll ask. And you have all of it ready.

What signals depth (without over-explaining)

Four language moves that make you sound like you've shipped this:

Instead of…Say…Why it works
"It saves money" "cache reads cost ~0.1× base input price" Quantification shows you know the economics
"You need a big prompt" "there's a model-dependent minimum — usually 1K tokens — below which it silently does nothing" "silently does nothing" signals you've been burned
"It might not work" "I'd verify by checking cache_read_input_tokens in the usage object" Names the exact diagnostic — shows you know how to debug it
"You should cache the static parts" "the invariant is: stable content must physically precede volatile content in the rendered prompt" States the rule, not just the instance

Recognizing question types — classify fast

The Classify step is fastest when you have a mental map of recurring patterns. These are the four prompt caching question types you'll see:

PatternSignal words in the questionYour classify sentence
Large static context + variable queries "handbook", "document", "knowledge base", "50 pages" "This is a large shared context pattern — cache the document, not the queries."
Multi-turn conversation "chatbot", "conversation history", "turns", "session" "This is incremental conversation caching — each turn extends the cached prefix."
Few-shot examples shared across requests "same examples", "consistent formatting", "10 examples every time" "This is shared prefix caching — cache the examples, vary only the input."
Debugging a cache miss "not working", "still expensive", "cache_read_input_tokens is zero" "This is a silent invalidator hunt — diff the rendered bytes between two requests."

The one-card cheat sheet

C — Classify: Name the pattern in one sentence. ("This is a large-static-context pattern.")

A — Apply: Tell them what you'd do and why, specifically. 2–3 sentences max.

T — Trap: Name one real failure mode. "The gotcha is…" Then stop.

Depth map: Layer 1 (mechanism) always. Layer 2 (tradeoff) briefly. Layer 3 (edge case) only when probed.
