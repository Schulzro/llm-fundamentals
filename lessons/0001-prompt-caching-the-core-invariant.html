Prompt Caching: The One Invariant

~12 min · Interview target: explain prompt caching in 2 min, cold

The one thing to hold in memory

Prompt caching is a prefix match. Any change anywhere in the prefix invalidates everything after it.

Everything else about prompt caching — where to put markers, what breaks it, when to use it — follows directly from this single fact. Nail it and the rest is bookkeeping.

What "prefix" actually means

When you call the Claude API, your request has three sections, always rendered in this order:

tools  →  system  →  messages

The API hashes the exact bytes up to each cache_control breakpoint you mark. On the next request, it checks: does the prefix match byte-for-byte up to that breakpoint? If yes → cache hit. If anything changed, even one character → miss, and you pay full price.

This means a timestamp embedded in your system prompt, a reordered JSON key in a tool definition, or a different user ID injected at the top — any of these silently kills caching for everything downstream of that change.

How to mark a cache breakpoint

Add cache_control to any content block — system text, tool definitions, message content:

{
  "type": "text",
  "text": "You are a helpful assistant. [... 2,000 tokens of instructions ...]",
  "cache_control": {"type": "ephemeral"}
}

The marker says: "cache everything up to and including this block." You get up to 4 breakpoints per request. The most common pattern is one breakpoint at the end of your system prompt.

TTL and cost — the numbers that come up in interviews

TTL optionWrite costRead costBreak-even reads
ephemeral (5 min, default)1.25× base0.1× base2 requests
ephemeral, ttl: "1h"2× base0.1× base3 requests

The write is expensive. A cold write costs more than the uncached base price. You only win if subsequent reads are frequent enough to pay it back. 5-min TTL breaks even at 2 requests; 1-hour TTL needs 3.

Minimum cacheable size — the gotcha interviewers love

Caching silently does nothing if your prefix is too short. No error — you just see cache_creation_input_tokens: 0 in the response.

Model familyMinimum tokens
Claude Opus 5, Fable 5 (newest)512
Opus 4.8, Sonnet 5, Sonnet 4.61,024
Opus 4.7, Haiku 3.52,048
Opus 4.6, Haiku 4.54,096

The minimum is not monotonic. Newer ≠ lower threshold in all cases. A 3K-token prompt caches on Opus 4.8 (1K min) but silently fails on Haiku 4.5 (4K min). This is a common interview trap — don't say "newer models are always more cache-friendly."

How to verify it's working

Check the usage object in the response:

"usage": {
  "input_tokens": 42,                  // uncached remainder only
  "cache_creation_input_tokens": 2800, // paid 1.25× to write cache
  "cache_read_input_tokens": 0         // on first request — expected
}

On the second request with an identical prefix:

"usage": {
  "input_tokens": 42,
  "cache_creation_input_tokens": 0,
  "cache_read_input_tokens": 2800     // paid 0.1× — cache hit!
}

Diagnostic rule: if cache_read_input_tokens stays zero across repeated identical requests, a silent invalidator is at work — diff the rendered prompt bytes between two requests to find it.

input_tokens is the uncached remainder only. Total prompt size = input_tokens + cache_creation_input_tokens + cache_read_input_tokens. Interviewers sometimes ask "how big was your prompt?" — don't read just input_tokens.

Your 2-minute interview answer

"Prompt caching lets you pay once to store the expensive part of your prompt — usually the system instructions or a large context block — and then serve subsequent requests at about one-tenth the cost. It works as a prefix match: you mark a breakpoint in your prompt, the API hashes everything up to that point, and if the next request matches byte-for-byte it returns a cache hit. The catch is that any change before the breakpoint — a timestamp, a reordered key, a user-specific injection — invalidates everything downstream. You also need your prefix to exceed a model-dependent minimum (usually 1K tokens) or caching silently does nothing. You verify it's working by checking cache_read_input_tokens in the response usage object."
